# maliwddm: memory and submission model

How `maliwddm` gives the Mali to Windows. The code points here by path
(`command.c`, `memory.c`, `maliwddm.h`, `maliwddm_abi.h`, the INF), so the
file keeps its old name. WDDM 2.0, the default, changes the version and the
paging node but keeps this model; see [WDDM2.md](WDDM2.md). WDDM 1.3
(`WddmProbe` 0x1300, or after a fallback) is the model below as it stands.
Settings: see [SETTINGS.md](SETTINGS.md).

The shape follows virtio-win's viogpu3d
([PR 943](https://github.com/virtio-win/kvm-guest-drivers-windows/pull/943)),
a WDDM 1.3 driver whose UMD is also Mesa's d3d10umd.

## Memory

The KMD owns the Mali's GPU address space; VidMm only decides residency.

- One aperture segment. `DxgkDdiCreateAllocation` reserves the
  allocation's Mali GPU address range (the malikm VA allocator, with the
  16 MB window for executable buffers) and returns the address to the UMD
  in the allocation's private data.
- `MAP_APERTURE_SEGMENT`: VidMm made the allocation resident; the driver
  maps its pages (from the MDL) at that fixed address in the Mali MMU.
- `UNMAP_APERTURE_SEGMENT`: evicted; unmapped. The address stays reserved
  and never changes, so `Patch` has nothing to patch.
- Every allocation in a submission's list is resident while it runs.
- Other paging operations return `STATUS_NOT_SUPPORTED`.

## Submission

- UMD: Panfrost's `SUBMIT` (job chain head and slot) becomes a command in
  the command buffer passed to `pfnRenderCb`, with its BOs in the
  allocation list.
- `DxgkDdiRender` validates and copies the commands into the DMA buffer and
  records a driver command in the DMA buffer's private data.
- `DxgkDdiSubmitCommand` starts the chains on the job slots and remembers
  `SubmissionFenceId`.
- Job done: `DxgkCbNotifyInterrupt(DXGK_INTERRUPT_DMA_COMPLETED)` and the
  DPC. Job fault: reported, and TDR resets.
- One node (the job manager). Preemption: see `TimeSlice` and
  `PreemptAnswer` in [SETTINGS.md](SETTINGS.md) and "TDRs with no job
  fault" in [PERF.md](PERF.md).

## Display

The display half came from `malidod`. Primaries are scanned out by the VOP2
directly ([PERF.md](PERF.md), stage 2); `ScanOut` 0 falls back to copying
into the firmware framebuffer. VOP2 register reads can drop the signal on
this SoC, so the driver only writes them. HDMI and modes:
[HDMI-HPD.md](HDMI-HPD.md), [DISPLAY-MODES.md](DISPLAY-MODES.md).

## Tests

The MMU and submission logic are shared with malikm (`drivers/common`) and
covered by `tests/malikm-host`; see [M3.md](M3.md).
