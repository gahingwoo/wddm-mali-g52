# M5.2: the full WDDM driver

Written 2026-10-02, after M4 (first triangle) and M5.1 (malidod drives the
display) passed on the board. It replaces the WDDM 2.0 / GpuMmu route in
[M5-PLAN.md](M5-PLAN.md) with something smaller that has been done before.

## The precedent: viogpu3d

virtio-win's viogpu3d ([PR 943](https://github.com/virtio-win/kvm-guest-drivers-windows/pull/943),
BSD-3, draft since 2023) is a full WDDM driver whose user-mode half is
**Mesa's d3d10umd**, the frontend we already run Panfrost under, with a
WDDM winsys for virgl ([Mesa MR 24223](https://gitlab.freedesktop.org/mesa/mesa/-/merge_requests/24223),
draft). Its known-issues list reports rendering glitches in WinUI3 apps;
WinUI3 apps reach the screen only through DWM's composition, so DWM runs on
a d3d10umd-based UMD there. That is the strongest evidence yet against the
top risk in M5-PLAN ("does DWM accept a UMD with only the D3D10/10.1 DDI?").
It is evidence, not a measurement on our board.

What it settles about the shape:

| | viogpu3d | for the Mali |
|---|---|---|
| WDDM version | 1.3 (`DXGKDDI_INTERFACE_VERSION_WDDM1_3`, caps `DXGKDDI_WDDMv1_3`) | the same; no GpuMmu, no WDDM 2.0 |
| memory | one aperture segment; VidMm hands the driver each allocation's pages (an MDL) in `BuildPagingBuffer(MAP_APERTURE_SEGMENT)` | the same; the driver maps those pages into the **Mali MMU** |
| paging operations | only map / unmap aperture segment; everything else `STATUS_NOT_SUPPORTED` | the same to start |
| engines | one node | one node (the job manager) |
| submission | `Render` copies the UMD's command buffer into the DMA buffer and keeps a pointer in the DMA buffer's private data; `SubmitCommand` finds it there | the same; a command is a list of Mali job chains |
| UMD | d3d10umd + virgl winsys over the D3D runtime callbacks | d3d10umd + Panfrost, with a WDDM `pan_kmod` backend |

## Why WDDM 1.3 fits the Mali

Panfrost needs a buffer's GPU address when it creates the buffer, and writes
it into descriptors. WDDM 1.x has no GPU virtual addressing of its own, so
the driver keeps one, exactly as malikm does:

- `DxgkDdiCreateAllocation` reserves the allocation's Mali GPU address range
  (the malikm VA allocator, including the 16 MB window for executable
  buffers) and returns the address to the UMD in the allocation's private
  data.
- `MAP_APERTURE_SEGMENT`: VidMm has made the allocation resident; map its
  pages at that fixed address (malikm's `MkMmuMap`, pages from the MDL instead
  of `MmAllocatePagesForMdlEx`).
- `UNMAP_APERTURE_SEGMENT`: evicted; unmap. The address stays reserved, so it
  never changes for the UMD.
- VidMm guarantees every allocation in a submission's allocation list is
  resident while the submission runs, which is the guarantee malikm had to
  build itself with BO lists and zombies.

`Patch` has nothing to patch: addresses never move.

## Submission

- UMD: Panfrost's `SUBMIT` (a job chain head and slot) becomes a command in a
  command buffer passed to `pfnRenderCb`, with its BOs in the allocation list.
- `DxgkDdiRender`: validate and copy commands into the DMA buffer; record a
  driver-side command in the DMA buffer's private data.
- `DxgkDdiSubmitCommand`: start the job chains on the job slots (malikm's
  `RunJob` register sequence), remembering `SubmissionFenceId`.
- Interrupt: job done -> `DxgkCbNotifyInterrupt(DXGK_INTERRUPT_DMA_COMPLETED,
  fence)` and queue the DPC; job fault -> report a fault and let TDR reset.
- No preemption (viogpu3d does the same; it is the next thing to learn).

## Display

malidod's code, unchanged in substance, plus `DxgkDdiSetVidPnSourceAddress`
once primaries live in our segment: first by copying the primary into the
firmware framebuffer (what malidod does now, from the DMA path), later by
writing the VOP2 ESMART0 window address (writes only; reads of VOP2 registers
can drop the signal on this SoC).

## Steps

| | Step | Done when |
|---|---|---|
| a | **maliwddm KMD skeleton**: DxgkInitialize with the viogpu3d DDI set, malidod's display, caps WDDMv1_3, one node, one aperture segment; Render/SubmitCommand complete every DMA buffer at once | installed with a stub UMD, the adapter starts and the desktop still works (on WARP via the stub? or a passthrough) |
| b | GPU in the KMD: malikm's power-up, MMU and job slots; aperture map/unmap into the Mali MMU; job submission with fences | a test that submits a WRITE_VALUE job through D3DKMT calls passes — **done 2026-10-02** in WinPE ([result](results/m5.2-step-b-2026-10-02.md)) |
| c | UMD: d3d10umd hardware path (from MR 24223's gdikmt) + Panfrost `pan_kmod` WDDM backend | the M4 triangle on `D3D_DRIVER_TYPE_HARDWARE` |
| d | Present to the screen: primaries, flips | a D3D11 window app on the Mali |
| e | DWM on the Mali | the desktop composites on the GPU |

The host test approach carries over: the MMU and submission logic stay
shared with malikm (`gpu.c`), already covered by tests/malikm-host.

## Open questions

1. Step (a) needs *some* UMD for the adapter to be usable: an adapter whose
   UMD fails to load leaves DWM without a device. Options: ship d3d10umd with
   softpipe as the first UMD (no GPU use, but a working D3D device), or have
   the INF name no UMD and see what Windows does. To be measured.
2. Does Windows 11 23H2 load a WDDM 1.3 full driver? viogpu3d targets
   Windows 10 and later; not confirmed for 11 here.
3. The aperture segment size and whether VidMm ever asks for Transfer/Fill
   with only an aperture segment (viogpu3d suggests not).
