# M3: Panfrost on the Mali under Windows

Written 2026-10-02. The code is done and builds in CI; none of it has run on
the board yet.

## Shape

```
triangle.exe (D3D11, D3D_DRIVER_TYPE_SOFTWARE)
  -> libgallium_d3d10.dll: Mesa's d3d10umd + Panfrost       (mesa.yml)
       Panfrost's Linux kernel backend, panfrost_kmod.c, unchanged
       -> win32-compat/malikm_drm.c: libdrm and mmap shim
            -> DeviceIoControl(\\.\MaliG52)
               -> drivers/malikm: KMDF, Linux Panfrost uAPI 1.1    (ci.yml)
                    -> Mali-G52 registers, AS0, job slots 0 and 1
```

Panfrost already talks to the kernel through a narrow, documented interface:
the Panfrost DRM uAPI. Rather than write a Windows backend for Panfrost, the
driver implements that uAPI, so the Mesa side needs no new code beyond the
shim.

## The ABI (include/malikm_ioctl.h)

- `IOCTL_MALIKM_DRM` carries one DRM ioctl: a header (DRM number, struct size,
  result) followed by Mesa's own struct. Arrays a struct points to are copied
  in after it and the pointer becomes an offset, so the driver never touches
  user memory. Absolute deadlines become relative on the way in.
- `IOCTL_MALIKM_MAP` / `UNMAP` are `mmap` / `munmap`. They need the calling
  process, so every request is handled in `EvtIoInCallerContext`.
- `IOCTL_MALIKM_VERSION` answers `drmGetVersion`: "panfrost" 1.1, the oldest
  version Mesa accepts, which keeps it off timestamps, JM contexts, BO sync
  and labels.
- Two non-DRM numbers export and import a syncobj's fence as a sequence
  number; that is all a sync file is to Panfrost.

Implemented: GET_PARAM, CREATE_BO, MMAP_BO, GET_BO_OFFSET, WAIT_BO, MADVISE,
SUBMIT, GEM_CLOSE, syncobj CREATE / DESTROY / WAIT / RESET / SIGNAL.

## Simplifications

| Linux Panfrost | malikm | cost |
|---|---|---|
| per-process address spaces | one, AS0, for every client | no isolation between processes |
| jobs on three slots, scheduled by dependencies | one job at a time, in submission order | no overlap of vertex and fragment work |
| heap BOs grow on GPU fault | allocated whole (Mesa's tiler heap: 128 MB) | memory |
| BO eviction (MADVISE) | never purged | memory |
| devfreq, runtime PM | GPU stays at the firmware's clock, always on | power |
| fault recovery per slot | soft reset and re-init on any fault or 2 s timeout | a bad job costs everyone a reset |

The order rule makes in-fences free: every job a fence names was submitted
earlier, so it has finished before the next one starts.

## Things that are easy to get wrong here

- **Non-coherent GPU.** BO pages are allocated and mapped write-combined, page
  tables uncached; jobs clean and invalidate the GPU caches at start and end
  (`JS_CONFIG`). The driver issues `DSB SY` before every job start and MMU
  flush: the descriptors were written through a write-combined mapping on the
  submitting CPU, and the worker may run on another.
- **`off_t` is 32 bits on Windows.** Mesa carries the mmap offset in one, so
  the offset is the BO handle in pages, not in the high word as on Linux.
- **Executable BOs must not cross 16 MB.** The shader program counter is 24
  bits; the VA allocator keeps them inside one window, as Linux does.
- **Interrupt routing is not trusted.** One ISR serves all three lines and
  claims whichever block is pending, and the worker also polls the raw job
  status every millisecond. A wrong line order in the DSDT costs latency,
  not a hang.
- **m1probe binds the same device.** `tools/windows/m3-test.cmd` removes it
  first.

## Testing without the board: MALIKM_FAKE

With `MALIKM_FAKE=1` and no `\\.\MaliG52`, d3d10umd opens `NUL` instead
and the shim answers every ioctl itself, on the same marshalled buffers the
driver would get: buffers are plain memory, `GET_PARAM` returns this board's
G52 values (from Linux Panfrost's log), and every job completes the moment
it is submitted without running. `MALIKM_FAKE=2` also logs each call.

`mesa.yml` runs the triangle that way on the `windows-11-arm` runner, so
Panfrost's screen creation, the Bifrost compiler, command-stream building
and the shim's marshalling all run on Windows in CI. The Panfrost build is
`debugoptimized` for PDBs; a crash is re-run under cdb and a hang (120 s)
gets every thread's stack, both kept as artifacts. A second run with
`PAN_MESA_DEBUG=trace` keeps pandecode's dump of the job chains.

What it caught so far, each a real bug the board would also have hit:

1. d3d10umd handed Panfrost a NULL screen config; Panfrost reads its driconf
   options through it (mesa-patches/0014).
2. `nir_type_float32` (160) in an 8-bit `nir_alu_type` bitfield read back as
   -96: MSVC enum bitfields are signed, and 0011 had only caught the
   `enum x` ones, not typedef'd enums (0016).
3. Panfrost never initialises `dev->bo_map_lock`; a zeroed pthread mutex is
   valid on Linux, a zeroed CRITICAL_SECTION is not (win32-compat/pthread.h
   now uses simple_mtx).
4. Nothing set up the glsl type cache: GL frontends do before creating a
   screen, d3d10umd (TGSI only) never did, and Panfrost's NIR needs it
   (0014). This was the first failure after D3D11 had created a device on
   Panfrost.

## On the board

Copy to a USB stick: `malikm\` (CI artifact `malikm-arm64`), `m3test.exe`
(`m3test-arm64`), `mesa\libgallium_d3d10.dll` and `mesa\triangle.exe`
(`mesa-d3d10umd-panfrost-arm64`), and `tools/windows/m3-test.cmd`. Run the
script from an administrator prompt; everything lands in `m3-out.txt`.

1. **M3.1, the driver alone.** `m3test` runs M1's WRITE_VALUE job on each slot
   through the uAPI, then 1000 jobs to time the round trip. PASS is the gate
   for the rest.
2. **M3.2, Mesa on the driver.** The triangle program with
   `GALLIUM_DRIVER=panfrost`, then again with `PAN_MESA_DEBUG=sync`, which
   waits for every job and reports GPU faults.

The driver writes its progress and counters (`Step`, `JobsDone`,
`JobsFailed`, `LastJsStatus`, `LastMmuFault`, `Resets`, ...) to
`HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP7402\0\Device Parameters`;
the script dumps that key before and after.
