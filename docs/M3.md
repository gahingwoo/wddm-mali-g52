# Panfrost on Windows: Mesa, malikm and the shim

How Mesa's Panfrost runs on Windows, and `malikm`, the plain kernel driver
it first ran on. `maliwddm` reuses the GPU code (`drivers/common`) and the
shim; see [M5.2-PLAN.md](M5.2-PLAN.md) and [WDDM2.md](WDDM2.md) for the
WDDM driver.

## Shape

```
triangle.exe (D3D11, D3D_DRIVER_TYPE_SOFTWARE)
  -> libgallium_d3d10.dll: Mesa's d3d10umd + Panfrost       (mesa.yml)
       Panfrost's Linux kernel backend, panfrost_kmod.c, unchanged
       -> win32-compat/malikm_drm.c: libdrm and mmap shim
            -> DeviceIoControl(\\.\MaliG52)
               -> drivers/malikm: KMDF, Linux Panfrost uAPI 1.1    (ci.yml)
                    -> Mali-G52 registers, AS0, job slots 0 and 1
```

The driver implements the Panfrost DRM uAPI, so Mesa needs no new backend,
only the shim.

## Mesa on Windows

- Mesa 26.2.0 is the last release with the D3D10 frontend (d3d10umd,
  removed upstream on 2026-09-30). It is pinned there. d3d10umd is a
  software-driver interface (the same DDI as WARP); our patches add the
  hardware path.
- Panfrost is built with clang-cl (MSVC ABI, GNU C accepted). The Bifrost
  encodings are packed explicitly because MSVC lays out mixed-type
  bitfields differently and makes enum bitfields signed; every enum-typed
  bitfield is unsigned. CI checks the packing against GCC on Linux.
- libpan is built without LLVM on Windows: the Linux CI job generates the
  SPIR-V and bindings, and two Python stand-ins for `mesa_clc` and
  `vtn_bindgen2` copy them in.
- `PACKED` must be real under clang-cl (`-DHAVE_FUNC_ATTRIBUTE_PACKED`).
- The patches are in [mesa-patches/](../mesa-patches/), the POSIX and libdrm
  shims in [win32-compat/](../win32-compat/).

## The ABI (include/malikm_ioctl.h)

- `IOCTL_MALIKM_DRM` carries one DRM ioctl: a header (DRM number, struct
  size, result) and Mesa's struct. Arrays are copied in after it and the
  pointer becomes an offset, so the driver never touches user memory.
  Absolute deadlines become relative.
- `IOCTL_MALIKM_MAP` / `UNMAP` are `mmap` / `munmap`, handled in
  `EvtIoInCallerContext`.
- `IOCTL_MALIKM_VERSION` answers "panfrost" 1.1, the oldest version Mesa
  accepts, which keeps it off timestamps, JM contexts, BO sync and labels.
- Two more numbers export and import a syncobj's fence as a sequence number.

Implemented: GET_PARAM, CREATE_BO, MMAP_BO, GET_BO_OFFSET, WAIT_BO, MADVISE,
SUBMIT, GEM_CLOSE, syncobj CREATE / DESTROY / WAIT / RESET / SIGNAL.

## Simplifications

| Linux Panfrost | malikm |
|---|---|
| per-process address spaces | one, AS0, for every client |
| three slots, scheduled by dependencies | one job at a time, in submission order (so in-fences are free) |
| heap BOs grow on GPU fault | allocated whole (tiler heap 128 MB) |
| BO eviction (MADVISE) | never purged |
| devfreq, runtime PM | firmware's clock, always on |
| fault recovery per slot | soft reset and re-init on any fault or 2 s timeout |

## Easy to get wrong

- **Non-coherent GPU.** BO pages are write-combined, page tables uncached;
  jobs clean and invalidate the GPU caches at start and end (`JS_CONFIG`).
  `DSB SY` before every job start and MMU flush.
- **`off_t` is 32 bits on Windows.** The mmap offset is the BO handle in
  pages.
- **Executable BOs must not cross 16 MB** (24-bit shader PC).
- **Interrupt routing is not trusted.** One ISR serves all three lines and
  the worker also polls the job status every millisecond.
- **m1probe, malikm and maliwddm bind the same device**; only one can be
  installed. `tools/windows/m3-test.cmd` removes m1probe first.

## GPU bring-up

What the firmware (edk2-rk3576) and the driver do before a job runs:

1. Supply `vdd_gpu_s0` (RK806 DCDC5) on. Linux switches unused regulators
   off after 30 s; Panfrost-less Linux needs `regulator_ignore_unused`.
2. Clock: `CLKSEL_CON(165)` = GPLL / 6 (198 MHz) at hand-over. The reset
   default selects AUPLL.
3. Power domain: ungate `CLK_GPU` and `PCLK_GPU_ROOT` (`CLKGATE_CON(69)`
   bits 1, 3, 8) and the PMU clock (0x140 bit 0); clear PMU `PWR_CON1`
   bit 9; wait for status bit 25 clear and repair bit 25 set; clear `REQ0`
   bit 0 and wait for `ACK0`/`IDLE0` bit 0 clear. Any GPU register access
   before the ACK clears is an SError.
4. GPU: soft reset, then power the L2, tiler and shader cores.
5. MMU AS0: `TRANSTAB` = level-0 table | 0x7, `MEMATTR` = 0x888d88,
   `TRANSCFG` = 0, then `UPDATE`. Tables `pa | 3`, leaves `pa | 0x2C5`
   (type 1 even at level 3, no AF).
6. Job slot: head, affinity = shader cores, config = AS 0 | priority 8 |
   flush on start and end, then START.

The firmware does 1 to 3, the driver 4 to 6. `tools/m1/m1_raw.c` runs the
same WRITE_VALUE job from Linux userspace with no GPU driver loaded.

## Testing without the board

- **`MALIKM_FAKE=1`**: with no `\\.\MaliG52`, the shim opens `NUL` and
  answers every ioctl itself on the same marshalled buffers: plain memory,
  this board's `GET_PARAM` values, every job complete at once. `2` also
  logs each call. `mesa.yml` runs the triangle and `tests/d3d11-present`
  this way on `windows-11-arm`, and again with `PAN_MESA_DEBUG=trace` for a
  pandecode dump. A crash is re-run under cdb; a hang (120 s) gets every
  thread's stack. Both are kept as artifacts.
- **`tests/malikm-host`**: `gpu.c` and `uapi.c` build on Linux against a
  mock WDK and drive a simulated G52 (MMU walking the driver's page tables,
  WRITE_VALUE jobs). 135 checks under ASan/UBSan on every push. `device.c`
  is not covered.

## On the board

Copy `malikm\` (artifact `malikm-arm64`), `m3test.exe` (`m3test-arm64`),
`mesa\libgallium_d3d10.dll` and `mesa\triangle.exe`
(`mesa-d3d10umd-panfrost-arm64`) and `tools/windows/m3-test.cmd`. Run the
script as administrator; output goes to `m3-out.txt`.

1. `m3test`: WRITE_VALUE on each slot, WAIT_BO, then 1000 jobs timed. PASS
   is the gate for the rest.
2. The triangle with `GALLIUM_DRIVER=panfrost`, again with
   `PAN_MESA_DEBUG=sync` (waits for every job, reports GPU faults), then
   `present.exe` (red, green, blue in a small window). PASS prints
   `centre=0xff0000ff ... corner=0xffff0000 -> PASS`.

The driver writes `Step`, `JobsDone`, `JobsFailed`, `JobsTimedOut`,
`LastJsStatus`, `LastMmuFault`, `LastFaultAddress*`, `Resets` and `Irqs` to
`HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP7402\0\Device Parameters`; the
script dumps it before and after. `Irqs` 0 with jobs done means the
interrupt lines do not reach the driver (polling still works).
