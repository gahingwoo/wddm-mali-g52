# M5.2 board run 4 (build 96: WARP named as UMD), 2026-10-02

Windows no longer boots after the reboot that loads build 96: the first boot
sat ~7.5 min with no desktop and was reset by hand; later boots were reset
~13 s after ExitBootServices. No minidump, no MEMORY.DMP.

The driver's trace, read from the offline SYSTEM hive (Fedora, ntfs-3g read
only, hivexsh), ControlSet001\Enum\ACPI\RKCP7402\0\Device Parameters\maliwddm:

| Order | DDI | Result |
|---|---|---|
| 1 | QueryInterface | c00000bb (as always) |
| - | StartDevice | Started=1, GpuUp=1, GpuId 0x74021000, Build 0x60 (96) |
| 2 | QueryChildRelations | 0 |
| 3 | QueryAdapterInfo | DRIVERCAPS (0x228) ok; QAI 47, 10, 0 not supported; QAI 5 (0x20) ok |
| 4 | CreateDevice | 0 |
| 5 | BuildPagingBuffer | 0 |
| 6 | QueryDeviceDescriptor | c01d0001 (no EDID from us) |
| 7 | RecommendMonitorModes | 0 (MonitorAddMode 0) |
| 8 | EnumVidPnCofuncModality | **c01e030a STATUS_GRAPHICS_INVALID_FREQUENCY** (Fail_AddTargetMode) |
| 9 | ControlInterrupt | 0 |
| - | Escape | c000000d (someone's escape, not ours) |

Two conclusions:

1. Runs 1-3 failed with code 43 right after DRIVERCAPS because the adapter
   named no user-mode driver. Naming d3d10warp.dll was the only change, and
   the adapter went on to CreateDevice, paging and VidPN.
2. The target mode with unspecified frequencies, which a display-only
   driver must use (M5.1), is rejected for a full WDDM driver with
   INVALID_FREQUENCY. With no VidPN, Windows stops at boot.

Recovery: maliwddm disabled offline (Start=4); the volume was unclean, so
ntfs-3g refused to mount it read-write from Fedora.
